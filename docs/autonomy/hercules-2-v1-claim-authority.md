# Hercules 2.0 V1 - Decision-bearing claim authority

**Status:** Owner-required cross-milestone contract
**Scope:** Structured outputs that can influence Hercules workflow decisions
**Current implementation state:** M5 evidence substrate, M6 additive projection/read
boundary, and M7 isolated operator presentation are merged. M8 independent-evaluation
enforcement is pending. No production runtime wiring or authority change is enabled.

## 1. Requirement

Hercules must not treat an AI-generated claim as authoritative merely because an
agent, reviewer, evaluator, or summary states it confidently. A factual assertion
may influence a state transition, merge recommendation, approval, deployment, or
automatic action only after Hercules verifies it against exact, immutable primary
evidence bound to the same task, contract, iteration, and candidate.

Agent self-reports are non-authoritative. They may help locate evidence or explain
intent, but they cannot satisfy a criterion, produce a green outcome, or authorize
an action.

## 2. Classification

Every structured, decision-bearing assertion has exactly one status:

- `verified`: independently established from eligible primary evidence and a
  fresh exact binding;
- `inference`: a reasoned conclusion that is not itself directly established by
  the bound primary evidence;
- `unverified_pending`: a factual assertion for which verification is missing,
  incomplete, stale, contradictory, or still in progress; or
- `opinion`: preference, recommendation rationale, or subjective judgment that
  is not represented as an established fact.

`inference`, `unverified_pending`, and `opinion` may be displayed as advisory
context. They are never decision-eligible. A recommendation may contain opinion,
but every factual premise required for the recommendation must separately be
`verified` and decision-eligible.

## 3. Exact binding

A `verified` decision-bearing factual assertion is decision-eligible only when
its verification receipt binds every core authority input:

- assertion ID and canonical assertion payload hash;
- task ID;
- immutable contract version and hash;
- iteration ID;
- exact candidate revision or artifact identity;
- primary evidence manifest ID and hash;
- the exact evidence entries and acceptance criteria establishing the assertion;
- verifier identity, implementation/version, observation surface, and timestamp;
- verification receipt ID and hash.

When an evaluator or policy consumes the assertion, the resulting verdict or
decision record must additionally bind that exact evaluator and policy identity.
None of the core contract, candidate, primary-evidence, or receipt bindings may
be marked inapplicable or supplied by the caller.

The control plane derives decision eligibility from authoritative structured
records. A caller cannot set `verified` or `decisionEligible` directly. Free-form
agent prose and `agent_claim` evidence cannot be promoted by relabeling it.

## 4. Fail-closed rules

The decision projection must return `need_more_evidence` and allow no dependent
workflow action when any required binding or primary evidence is:

- missing or inaccessible;
- stale for the current contract, iteration, candidate, evidence manifest, or
  policy;
- contradictory, including any unresolved conflict between otherwise eligible
  primary observations;
- corrupt, hash-mismatched, replaced, or otherwise tampered;
- derived solely from an agent self-report, model narrative, summary, inference,
  or opinion; or
- insufficient to establish every factual premise on which the action depends.

`need_more_evidence` is not a pass and is distinct from implementation failure.
Reverification may collect evidence, but it cannot silently rewrite the candidate
or reinterpret the contract. A contradiction clears only through a new receipt
over a newly verified exact evidence set in which the conflict is no longer
present, never through a narrative assertion that it was resolved.

## 5. Decision boundary

No state transition, merge recommendation, approval, deployment recommendation,
deployment, or automatic action may consume raw prose as an authority input. Each
such path must consume a structured decision record whose required assertions all
pass the exact-binding eligibility check at the moment of use.

Human authority is preserved, but the interface must not present unverified
machine claims as verified facts. Any explicit human override authorized by a
future contract must remain separately typed, attributable, bounded, and audited;
this contract does not create such an override.

## 6. Honest coverage boundary

Hercules cannot technically guarantee that every sentence generated by every
model, log, or external tool is semantically classified correctly. The enforceable
boundary is narrower and complete: all structured outputs that can affect a
workflow decision, action, status, recommendation, approval, or deployment must
use this classification and eligibility gate, and no decision path may derive
authority from unstructured prose.

Ordinary narrative may be labelled for operator clarity, but labels alone do not
make it authoritative. The protection comes from excluding prose from authority
inputs and revalidating exact evidence bindings at decision time.

## 7. Milestone-scoped implementation

### M5 - Evidence substrate

- Preserve immutable content, provenance, trust class, exact candidate binding,
  tamper detection, and sealed archive history.
- Keep `agent_claim` non-primary and non-authoritative.
- Do not add runtime composition, decision projection, API, UI, or action wiring.

### M6 - Structured claim and decision projection

- Add strict assertion classification, verification receipt, and decision
  eligibility domain contracts.
- Derive assertion status and eligibility from authoritative records; reject
  caller-supplied authority flags.
- Project `need_more_evidence` for missing, stale, contradictory, tampered, or
  self-reported premises.
- Keep the V2 read API additive and existing consumers unchanged.

### M7 - Operator presentation

- Show verified fact, inference, pending verification, and opinion distinctly in
  every decision-bearing review surface.
- Never render pending or advisory assertions with green/approved semantics.
- Explain which exact binding or evidence is missing or stale, with real render
  and mobile L2 tests.

### M8 - Independent evaluation enforcement

- Require every factual premise of a verdict or recommendation to reference an
  eligible verified assertion.
- Reject implementer/reviewer/evaluator self-report as authority.
- Revalidate the exact contract/candidate/evidence/policy binding before emitting
  a verdict; fail closed to `need_more_evidence`.

### M9-M10 - Routing and worker containment

- Route evidence gaps only to reverification or bounded escalation.
- Do not let a worker result, retry narrative, or agent conclusion advance task
  state without the same authority check.

### M11 - API enforcement

- Expose typed status, bindings, receipts, and decision eligibility in V2 DTOs.
- Reject stale or ineligible decision requests server-side and prove a second
  client cannot bypass the rule.

### M12-M13 - Integrated proof

- Exercise the rule across code, browser, and bounded non-code tasks.
- Add held-out cases for confident false self-report, missing evidence, stale
  candidate/contract, contradictory primary evidence, tampered manifests, and
  prose attempting to trigger approval, merge, deployment, or automatic action.
- Prove all such cases remain non-green and actionless, while eligible verified
  assertions work through the additive V2 path.

## 8. Current prohibition

This document authorizes only the additive milestone implementation described
above. The merged M5/M6 substrate remains unwired, and later milestone code is
not production authority merely because it exists. This document does not
authorize production runtime wiring, authority cutover, production deployment,
automatic merge/approval, privileged actions, external side effects, or removal
of existing compatibility and rollback paths.
